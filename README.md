# Lingua Sacra Collatinus Analyzer

Lingua Sacra Analyzer is a full Latin morphological analyzer compiled from the
[Collatinus](https://github.com/biblissima/collatinus) linguistic data. It runs
locally in Node.js or a modern browser, makes no external API calls, and returns
every analysis supported by the underlying morphology rather than silently
choosing one interpretation.

It was built for the Lingua Sacra Reader, where a learner must be able to select
an inflected word in an Ecclesiastical Latin text, see all of its possible
lemmas and grammatical readings, and then open a separately sourced dictionary
entry. The analyzer is a standalone repository so the same engine can also
compile indexes for an entire digital library.

The current pilot integration is complete: the analyzer supplies the Reader's
morphology by building its per-text static index, while the same runtime remains
available for future live browser analysis. Reader-specific concerns such as
learner-facing abbreviations, contextual candidate ranking, source orthography
restoration, and Lewis & Short rendering deliberately remain outside this
package.

## What makes it different

### It is an analyzer, not a lookup table

The runtime performs Collatinus-style `stem + ending` analysis. It tests regular
inflectional matches, irregular forms, assimilations, contractions, and
suffixes at lookup time. It does not attempt to enumerate and ship every
possible Latin surface form.

This gives the project two complementary modes:

- **Live analysis** for words that have not been indexed yet.
- **Static indexes** for published texts, generated by the exact same runtime.

The two modes therefore cannot drift into different morphological answers.

### It preserves ambiguity by design

Many analyzers and taggers are optimized to return one contextually preferred
parse. That is useful for corpus annotation, but it hides information a learner
may need. Lingua Sacra Analyzer instead returns all structurally valid
lemma-analysis pairs. For example, `principio` retains both nominal readings
and the possible verb reading; `gratiæ` retains genitive singular, dative
singular, nominative plural, and its other supported interpretations.

Candidates are ordered by Collatinus lemma frequency only as a stable default.
Those counts come from the classical Latin texts of the LASLA corpus; they are
not Vulgate-specific or Ecclesiastical Latin frequency measurements. The order
is therefore not presented as a contextual grammatical judgment. A reader
application can add an auditable contextual ranking layer while keeping every
candidate available.

### It is local-first without a server or native runtime

Upstream Collatinus provides the linguistic models and mature analysis logic.
This project turns those resources into compact JSON data and reimplements the
runtime in TypeScript. As a result, applications do not need:

- an external morphology API;
- a Python service in production;
- a native executable or WebAssembly bundle; or
- a network round trip for each word.

Node and browser environments share the same analyzer class. Only the data
loader changes: filesystem reads in Node, `fetch` in a browser.

### Browser delivery is sharded and lazy

The complete compiled data set is about 25 MB uncompressed, but a lookup does
not load it all. The browser first loads a small shared core, then caches only
the two-letter radical and irregular shards and the hashed lemma shards required
by the words a user actually requests.

The current compiled corpus contains:

| Resource | Count |
| --- | ---: |
| Lemmas | 81,839 |
| Radical records | 152,478 |
| Ending/model/morphology combinations | 9,073 |
| Irregular surface-form keys | 71 |
| Hashed lemma shards | 64 |

### It normalizes common Vulgate spellings

Input normalization handles ligatures and common orthographic equivalences:
`æ → ae`, `œ → oe`, `j → i`, `v → u`, and removal of vowel quantity or other
combining marks. The original surface form is retained in the response while
the normalized form is used for analysis and index keys.

English-gloss linkage follows a separate, conservative rule. It first tries an
exact Collatinus lemma/headword match. Only when that produces no English gloss
does the compiler try controlled `u → v`, `i → j`, and combined orthographic
variants. This recovers entries such as `uideo → video`, `uita → vita`, and
`uoco → voco` without merging a variant into an available exact match.

### Morphology and dictionary content remain separate

The analyzer includes Collatinus lemma metadata, noun gender, generated verb
principal parts, LASLA frequency counts, and short English glosses from the
Collatinus data. Noun gender is compiled directly from the morphological
indicator in `lemmes.la`/`lem_ext.la`; it is not guessed from the inflectional
model or inferred from Lewis & Short.

The analyzer does not bundle Lewis & Short or pretend that a morphological
candidate is automatically the correct dictionary sense.

The Lingua Sacra Reader links analyzer lemmas to separately generated Lewis &
Short shards by exact normalized headword. This separation allows morphology,
contextual ranking, and displayed dictionary content to be reviewed and updated
independently.

## How it was built

The build has two layers:

1. **Python compiler.** `scripts/compile_collatinus.py` reads a pinned Collatinus
   checkout through `pycollatinus`, extracts the lemma models, radicals,
   endings, morphology labels, irregulars, assimilation rules, contractions,
   suffixes, noun genders, frequency counts, and English glosses, and writes
   stable, compact JSON records.
2. **TypeScript runtime.** `src/analyzer.ts` reconstructs the relevant
   Collatinus matching process over those records. `FileSystemDataSource` and
   `FetchDataSource` provide Node and browser delivery without changing the
   analysis logic.

The source revisions used to generate the checked-in data are recorded in
`sources.lock.json`. The current data was compiled from Collatinus commit
`a0eb15bb0acce74b2baf3d4a4adcea9c4f63aaf5` with `pycollatinus` 0.1.6.
The checked-in manifest uses analyzer schema version 2, which added explicit
noun gender to each lemma record.

For each lookup, the runtime:

1. normalizes the surface form;
2. generates permitted assimilation, contraction, and suffix variants;
3. checks irregular-form records;
4. tries every possible split between a radical and ending;
5. accepts only matching model and radical-number combinations while respecting
   excluded morphologies;
6. loads the matching lemma metadata;
7. removes duplicate analyses; and
8. groups the results by lemma without discarding ambiguity.

Verb dictionary headings are generated from the model itself, which is why a
form such as `erat` is presented under `sum, esse, fui, futurus` rather than an
opaque lemma key.

## Repository layout

```text
scripts/compile_collatinus.py  Collatinus-to-JSON compiler
src/analyzer.ts                Shared analysis engine
src/browser-loader.ts          Fetch-backed data source
src/node-loader.ts             Filesystem-backed data source
src/cli.ts                     Analyze and index commands
public/data/                   Compiled, browser-loadable shards
tests/                         Morphology and ambiguity checks
sources.lock.json              Pinned upstream revisions
```

## Build the runtime

```sh
npm install
npm run check
```

`npm run check` compiles the TypeScript and runs the analyzer tests.

## Regenerate the analyzer data

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
git clone https://github.com/biblissima/collatinus.git .cache/collatinus
git -C .cache/collatinus checkout a0eb15bb0acc
.venv/bin/python scripts/compile_collatinus.py \
  --collatinus-root .cache/collatinus \
  --output public/data
```

The compiler records the resolved full Collatinus commit in the generated
manifest. Generated shards should be regenerated from the pinned source rather
than edited by hand.

## Use from Node.js

```ts
import {
  CollatinusAnalyzer,
  FileSystemDataSource,
} from "@lingua-sacra/collatinus-analyzer";

const analyzer = new CollatinusAnalyzer(
  new FileSystemDataSource("public/data"),
);

const result = await analyzer.analyze("gratiæ");
console.log(result.lemmas);
```

## Use in a browser

Copy or serve `public/data` at a stable URL, then point the fetch-backed loader
to it:

```ts
import {
  CollatinusAnalyzer,
  FetchDataSource,
} from "@lingua-sacra/collatinus-analyzer";

const analyzer = new CollatinusAnalyzer(
  new FetchDataSource("/collatinus-data"),
);

const result = await analyzer.analyze("principio");
```

Run the included browser demo with:

```sh
npm run demo
```

## Use the CLI

Analyze one or more words:

```sh
npm run build
node dist/cli.js analyze erat principio gratiæ --data public/data
```

Build a static index from a newline-delimited list of unique forms:

```sh
node dist/cli.js index \
  --input forms.txt \
  --output index.json \
  --data public/data
```

The output key is the normalized surface form and the value is the same
`AnalysisResult` returned by live analysis.

## Response contract

Each result contains:

- the original and normalized surface forms;
- whether the form was recognized;
- the total analysis count;
- every matching lemma with its headword, generated dictionary heading, part
  of speech, noun gender, inflectional model, LASLA frequency, and short English
  glosses; and
- every morphology with its numeric Collatinus ID, English label, matched stem
  and ending, and whether it came from a regular, irregular, or Roman-numeral
  rule.

This separation lets consuming applications log a surface-form encounter,
display all morphology, attach dictionary records, and rank candidates in
context without rewriting the analyzer's source data.

The public response preserves full English morphology labels such as
`perfect indicative active 3rd singular`. Compact labels such as
`perf. indic. act. 3rd sing.` are a presentation concern and are not stored in
the analyzer data.

## Integration contract

The analyzer owns:

- orthographic normalization and morphology lookup;
- all structurally valid lemma-analysis pairs;
- lemma metadata, noun gender, generated verb headings, frequency, and short
  glosses;
- deterministic live and batch analysis; and
- browser- and filesystem-backed loading of the same compiled data.

A consuming reader owns:

- restoration of the source text's displayed `v/u`, `j/i`, and ligature choices;
- learner-facing declension, conjugation, and morphology abbreviations;
- contextual ranking or reviewed overrides, without deleting alternatives;
- dictionary attachment and rendering; and
- lookup logging or learner-model behavior.

For a growing library, the intended deployment pattern is to run
`analyzeMany()` at build time for each text and ship that small per-text index.
The live browser analyzer remains available as a fallback and for texts that
have not yet been indexed. Both paths return the same `AnalysisResult` contract.

## Validation and current scope

The automated tests cover irregular forms of `sum`, ambiguous noun/verb forms,
Vulgate ligatures, noun-case ambiguity, regular perfect verbs, principal-part
generation, noun gender, controlled `u/v` English-gloss linkage,
deduplication, and static-index consistency. Against the current three-chapter
Reader pilot, the analyzer recognizes 791 of 794 unique forms (99.6%). That is
a pilot measurement, not a claim of universal Ecclesiastical Latin coverage.

Important current boundaries:

- the linguistic foundation is Collatinus and remains primarily a Latin
  morphological lexicon, not a syntactic parser;
- candidate frequency is not contextual disambiguation;
- project-specific Ecclesiastical vocabulary and spelling aliases still need a
  reviewed overlay;
- a missing form remains visibly unrecognized instead of being guessed; and
- software and linguistic-data licensing must be cleared before a public
  distribution.
